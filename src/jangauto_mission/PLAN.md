# ㄹ자 커버리지 경로 앱 연동 검증 — 남은 항목 (다음 라운드용)

## Context

오늘 앱(Android)과 실제로 연동해서 ㄹ자 커버리지 경로 생성→선택→RUN 주행
전체 흐름을 처음으로 검증했다. 경로 생성/선택 쪽에서 버그 2개, RUN 주행
쪽에서 버그 1개를 찾아 고쳤고(아래 기록), 실제 Nav2 주행까지는 확인했지만
완주 후 동작과 주행 초반에서 새 문제 2개를 추가로 발견했다. 시간 관계상
이 둘은 조사/수정을 다음으로 미룬다.

## 이번에 찾아서 고친 버그 (참고용 기록)

1. **`select_coverage_path`의 `msg_id`**가 앱에서 다른 명령들과 동일한
   관례대로 매번 새로 생성되고 있었음 — 로봇은 이 필드가 직전
   `coverage_path_result`를 참조하길 기대해서 매번 거부됨. 참조용
   `ref_msg_id` 필드를 새로 분리해서 해결(커밋 `5080b50`).
2. **`_on_app_ack`**가 `coverage_path_result`에 대한 `app_ack`을 받자마자
   후보 데이터(`_pending_coverage_path`)를 통째로 지워버려서, 사용자가
   실제로 화면 보고 select 하기 전에 참조할 데이터가 이미 사라져 있었음.
   ack는 재전송만 멈추고, 데이터는 select 성공 또는 새 generate 전까지
   유지하도록 수정(커밋 `9f2e022`).
3. **`run_action_server.py`의 `_send_and_wait()`**가 Nav2 서브골의 실제
   성공/실패를 확인하지 않고 취소 여부만 봐서, 실측 중
   `controller_server`가 타임아웃으로 진짜 실패했는데도 무시하고 다음
   단계(Spin 등)로 그냥 넘어가는 걸 확인함 — `GoalStatus`를 확인해서
   실패 시 Run 전체를 즉시 abort하도록 수정(커밋 `24538f2`).

## 남은 문제 (다음 라운드에서 조사/수정)

### 1. 경로 완주 후 자동 재시작 (sw_bits가 계속 RUN이면 처음부터 다시 도는 문제)

- **증상**: 선택한 경로를 끝까지 돈 뒤에도 앱이 sw_bits를 RUN에서 안
  내리면, 로봇이 시작점으로 되돌아가 경로를 처음부터 다시 시작한다.
  기대 동작은 "완주하면 마지막 지점에서 정지하고 대기"이지 반복 주행이
  아니다.
- **짐작되는 원인**: `mission_state_machine.py`(YASMIN)의 RUN 상태가
  `run` 액션을 호출해 성공한 뒤에도 sw_bits가 여전히 RUN이면 상태머신이
  같은 RUN 상태로 재진입해 액션을 다시 호출하는 구조로 보인다.
  `run_action_server.py`는 선택된 경로를 지우지 않으므로(사용자가 확정한
  "재선택 없이 재사용 가능" 정책) 재호출되면 그냥 처음부터 다시 실행된다.
- **확인/수정 방향**: `mission_state_machine.py`의 RUN 상태 진입/재진입
  로직을 읽고, "이번 RUN 진입에서 이미 완주했다"를 기억해 sw_bits가
  바뀌지 않는 한 액션을 재호출하지 않고 제자리 대기(정지)하도록 만들 것.
  단, 재선택/재생성이 오면 다시 실행 가능해야 하므로 기존 "경로 재사용"
  정책과 충돌하지 않게 설계할 것.

### 2. 시작점 부근에서 계속 맴도는 문제

- **증상**: 주행 초반에 로봇이 시작 지점 근처에서 계속 도는 것처럼
  보임(원인 미특정).
- **확인 필요**: 이게 위 1번(완주→재시작)이 짧은 주기로 반복돼서 "맴도는
  것처럼" 보이는 것인지, 아니면 진짜 별개로 첫 웨이포인트 근처에서
  Regulated Pure Pursuit 컨트롤러나 초기 정렬(yaw)에 실제 문제가 있는
  것인지 구분할 것. Gazebo 화면 육안 관찰 + `/cmd_vel_nav_out` 실측으로
  판단.
- 아래 collision_monitor 이슈(정지→재출발 반복)가 겹쳐서 맴도는 것처럼
  보이게 했을 가능성도 배제하지 말 것.

## 참고: 이번에 발견했지만 고치지 않은 이슈 (기능과 무관, 시뮬레이션 성능 추정)

- `collision_monitor`가 `/front_depth_camera/points`(depth_cloud)
  타임스탬프가 `source_timeout`(1.0초)을 넘겨 "invalid source"로 판단,
  반복적으로 로봇을 정지시킴. `use_sim_time`은 정상(`True`) 확인했고,
  `/clock` echo 중 메시지 드롭도 확인됨 — sim_time 설정 문제가 아니라 이
  머신의 연산 부하로 센서 파이프라인이 밀리는 것으로 추정. `source_timeout`
  을 늘리는 건 안전 마진을 깎는 임시방편이라 권장하지 않음 — 다음엔 검증
  세션 중 동시 작업(빌드/모니터링 등)을 줄이거나 별도로 조용한 환경에서
  재확인해볼 것.

## 테스트 시 유의사항 (이번 라운드에서 배운 것)

- 앱이 sw_bits를 계속 보내는 이상 상태머신이 계속 반응하므로, "한 번
  완료됐다"는 신호를 명확히 관찰하려면 완주 직후 sw_bits를 내려서
  재시작을 막고 관찰하는 편이 낫다(1번 문제 고치기 전까지의 임시 우회).
- `ros2 topic echo`/`ros2 topic hz`가 이 세션에서도 간헐적으로 빈
  응답/드롭을 보였다(이전 라운드 `jangauto_bringup/PLAN.md`에서도 겪은
  known issue) — 안 나오면 재시도하거나 rclpy로 직접 짧은 스크립트를
  짜서 재확인할 것.
- 백그라운드 로그를 키워드로 필터링할 때 짧은 영어 단어(`ack`, `goal`
  등)를 raw substring으로 매칭하면 무관한 단어(`lack` 등)에 오탐될 수
  있다 — 단어 경계(`\b`) 매칭을 쓸 것.
- 안드로이드 앱은 소스만 고치고 기존 설치본을 계속 쓰면 반영이 안 된다
  — 재빌드+재설치를 반드시 확인할 것.
