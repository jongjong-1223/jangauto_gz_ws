# 앱↔로봇 상태 전이 핸드셰이크 프로토콜

이 문서는 **스펙**이다 — 앱(Android) 저장소가 이 머신에 없어서 실제 Kotlin
코드는 여기서 수정할 수 없다. 아래 계약대로 앱 쪽을 구현/수정해야 한다.

로봇 쪽 구현: `jangauto_mission/scripts/mission_state_machine.py`(판단/발행) +
`jangauto_hmi/scripts/app_websocket_bridge.py`(웹소켓 중계, 내용 해석 없음).

## 1. 개념 변화: "상태 지정"이 아니라 "전이 요청"

- 앱이 보내는 와이어 포맷 자체(`sw_bits` 등 JSON)는 바뀌지 않는다.
- 다만 의미가 바뀐다: 이전엔 "내가 원하는 상태를 계속 알려주는 것"이었다면,
  이제는 **"이 상태로 전이해달라는 요청 하나"**로 해석해야 한다.
- 로봇은 이 요청을 항상 수락하지 않는다 — 순서 규칙(아래)에 안 맞으면 거부한다.
- 주기적 재전송(기본 500ms)은 그대로 유지한다 — 하트비트 역할을 겸하며,
  끊기면 로봇이 자동으로 STOP으로 전이한다.

## 2. 상태 전이 순서 규칙 (로봇이 강제)

- STOP/KEY/CAL은 서로 언제든 자유롭게 오갈 수 있다.
- ALIGN은 STOP/KEY/CAL에서만 요청할 수 있다.
- RUN은 ALIGN에서만 요청할 수 있다(STOP/KEY/CAL에서 RUN 직행 불가).
- **내려가는 요청은 항상 자유**: RUN/ALIGN에서 STOP/KEY/CAL로, RUN에서
  ALIGN으로 가는 요청은 지금 상태가 뭐든 항상 수락된다.
- 위 규칙과 무관하게, 로봇 내부 에러나 명령 타임아웃 시 로봇은 스스로
  STOP으로 전이한다 — 이건 앱 요청과 무관하게 일어나므로 앱은 §4의
  상태 미러로만 알 수 있다(§3의 ack로는 알 수 없음).

## 3. 로봇 → 앱: 명령 응답 (`/app/control_state_ack`)

앱이 control_state 메시지를 하나 보낼 때마다, 로봇이 정확히 1개의 JSON
응답을 웹소켓으로 돌려준다:

```json
{
  "sw_bits": 1,
  "requested_mode": "RUN",
  "accepted": false,
  "current_mode": "STOP",
  "reason": "STOP -> RUN not allowed"
}
```

필드 의미:
- `sw_bits`, `requested_mode`: 앱이 보낸 요청을 그대로 echo(별도 요청ID
  없이, 보낸 값 자체가 correlation 역할).
- `accepted`: 수락 여부.
- `current_mode`: 이 처리 직후 로봇의 실제 현재 상태 — **수락/거부와
  무관하게 앱은 항상 이 값에 자기 화면을 맞춰야 한다**(로봇이 진실의 소스).
- `reason`: 거부 시 사람이 읽을 수 있는 사유. 수락 시 빈 문자열.

## 4. 로봇 → 앱: 상태 미러 (`/app/robot_status`)

로봇의 현재 상태가 바뀔 때마다(원인이 앱 명령이든, 내부 에러든, 타임아웃이든)
발행되는 JSON:

```json
{"mode": "STOP", "in_error": false, "error_reason": ""}
```

- 웹소켓 접속 직후에도 즉시 한 번 보내준다(로봇이 latched 상태를 캐시해뒀다가
  새 접속에 바로 전송) — 그래서 앱은 접속하자마자 현재 상태를 알 수 있다.
- `in_error`가 true면 앱 명령과 무관하게(에러/타임아웃으로) STOP이 강제된
  상태라는 뜻 — `error_reason`에 사유가 담긴다.

## 5. 앱 UI 로직에서 바뀌어야 할 부분

- 명령을 보내는 즉시 "내가 요청한 상태"로 낙관적으로 화면을 바꾸지 말 것.
  §3의 ack 또는 §4의 상태 미러를 받은 뒤에만 화면을 갱신한다.
- `accepted: false` 응답을 받으면 `reason`을 사용자에게 표시한다
  (예: "RUN은 ALIGN 상태에서만 가능합니다").
- 화면의 "현재 로봇 상태" 표시는 앱이 마지막으로 보낸 값이 아니라, 항상
  로봇이 보내준 `current_mode`(§3) 또는 `mode`(§4)를 그대로 반영한다 —
  둘 중 어느 쪽이 최신이든 로봇이 보고하는 값이 화면과 다르면 화면을 그
  값으로 맞춘다(로봇이 authoritative, 앱은 항상 로봇에 싱크).
